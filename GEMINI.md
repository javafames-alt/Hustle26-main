# Правила разработки и стандарты кодовой базы

## 1. Чистота кода и отсутствие комментариев
- Запрещены комментарии (`//`, `/* */`, Javadoc): код должен быть самодокументируемым за счёт понятных и точных имён.
- Не добавлять лишних информационных полей, заглушек и мусора в код.
- Никаких временных fallback-костылей — только полноценные рабочие решения.

## 2. Оптимизация и производительность
- Компактность: сокращать объем кода с 50 до 20 строк везде, где это возможно без потери читаемости.
- Минимум static полей во избежание утечек памяти и нарушения архитектуры.
- Оптимизация условий: не использовать глубокую вложенность `if`, применять early return (guard clauses).
- Исключить дублирование логики (no duplicated code fragments), выносить повторы в чистые вспомогательные методы.
- Высокая производительность JVM:
  - Использовать структуры данных с минимальным оверхедом по памяти и быстрым доступом (примитивные коллекции, fastutil/caching).
  - Минимизировать аллокации объектов в hot-path (тиках, рендере, событиях боя).
- Предлагать высокопроизводительные библиотеки для оптимизации при необходимости.

## 3. Стиль и форматирование (IntelliJ IDEA)
- Строго соблюдать единый стиль существующей кодовой базы.
- Именование: все поля и методы исключительно в `camelCase` (без КАПСА и `snake_case`, кроме жестких требований сторонних API/enum).
- Форматирование по стандартам IntelliJ IDEA: без предупреждений (warnings), проблем синтаксиса и инспекций дубликатов.
- Использовать актуальные Minecraft Data Components вместо устаревших NBT-тегов.
- Использовать самые современные API, доступные в версии проекта.

## 4. Портирование и адаптация
- При переносе функционала не ссылаться на несовместимость версий: сразу выполнять прямую адаптацию под целевую версию.
- Портировать все запрашиваемые файлы целиком без сокращений и пропусков.
- Запрещено использовать скрипты Python для правки Java-кода.

## 5. Процесс работы и коммуникация
- Все ответы и пояснения давать на РУССКОМ языке.
- Перед написанием кода задавать уточняющие вопросы при неоднозначности требований.
- При обнаружении нерабочего кода сразу предлагать рабочую альтернативу с пояснением без костыльных решений.
